# Data Model: Installable PWA and Offline Use

Phase 1 output for [plan.md](plan.md). Two small server-side changes. Most of the feature's data lives on the device.

## 1. Server (Postgres via Prisma)

### `submissions`: new `client_op_id`

| Column | Type | Rule |
| --- | --- | --- |
| `client_op_id` | `uuid null unique` | The id of the last offline op applied to this row (research R7). Written by `/api/sync` only; online Server Actions leave it as it is, so a replay of an op whose answer was lost still reads as a duplicate after later edits. |

Prisma: `clientOpId String? @unique @map("client_op_id") @db.Uuid`, with the doc comment `/// offline idempotency key (spec 008 R7)`, matching `LessonProgress`.

### `shifts`: new `updated_at`

| Column | Type | Rule |
| --- | --- | --- |
| `updated_at` | `timestamptz not null default now()` | The version a queued edit or delete was made on (research R7). |

Prisma: `updatedAt DateTime @default(now()) @updatedAt @map("updated_at") @db.Timestamptz(6)`.
- Every shift write goes through Prisma (`repo.saveShift`, `repo.deleteShift`, `rotation-repo` `createMany`/`deleteMany`; no raw SQL writes, checked 2026-11-24), so `@updatedAt` keeps it current.
- Existing rows get `now()` from the default.

### Existing columns this feature starts writing

| Column | Written when |
| --- | --- |
| `lesson_progress.client_op_id` | an offline `progress.complete` or `progress.undo` applies |
| `study_sessions.client_op_id` | an offline `focus.record` inserts a session |
| `shifts.client_op_id` | an offline `shift.save` (edit) applies; a new shift is created with it |

These columns are `unique`, and each op id is a fresh uuid, so one op id is never on two rows.

### No new tables, policies, functions or Storage settings

- Both new columns sit on tables whose student policies already limit rows to the student (`subs_student_*`; the shifts policies from 005). RLS is unchanged.
- `/api/sync` reaches the tables through Prisma, behind the guards (contracts/sync-route.md).
- Offline photos upload to the existing `submissions` bucket under the existing path rule and policy (004 research R7).

### Migration

`prisma/migrations/<UTC timestamp>_offline_versions/migration.sql`, generated by diffing `schema.prisma` against git (docs/data-model.md §7). Expected SQL:

```sql
ALTER TABLE "submissions" ADD COLUMN "client_op_id" UUID;
ALTER TABLE "shifts" ADD COLUMN "updated_at" TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP;
CREATE UNIQUE INDEX "submissions_client_op_id_key" ON "submissions"("client_op_id");
```

Nothing to add by hand. Check the generated file drops nothing (no SQL-only object is touched).

### pgTAP (`supabase/tests/008_offline_versions.test.sql`)

- `submissions.client_op_id` exists and is unique: a second row with the same value fails.
- `shifts.updated_at` exists, is not null and has a default.
- As a student: updating another student's submission or shift, with `client_op_id` set, affects 0 rows (policies unchanged).

## 2. Device (IndexedDB via Dexie, database `studymate`, version 1)

Every row has `userId`. Sign-out deletes the database (R11). A different user signing in deletes other users' rows first (R10).

### `outbox`: queued writes (R5)

| Field | Type | Notes |
| --- | --- | --- |
| `id` | uuid (primary key) | The op id, sent as the idempotency key |
| `userId` | uuid | Owner. Only the signed-in user's rows are sent |
| `type` | `'progress.complete' \| 'progress.undo' \| 'submission.save' \| 'submission.submit' \| 'focus.record' \| 'focus.stop' \| 'shift.save' \| 'shift.delete'` | contracts/sync-route.md |
| `recordKey` | string | `progress:<lessonId>`, `submission:<lessonId>`, `focus:<opId \| sessionId>`, `shift:<shiftId \| opId>`; coalescing key |
| `payload` | object | The op's fields, parsed by the same Zod schema on the server |
| `base` | `{ wasDone: boolean } \| { updatedAt: string \| null } \| null` | What the student saw (R7) |
| `at` | ISO string | When the student acted (first enqueue; for Submit the press time) |
| `createdAt` | number | Replay order (FIFO) |
| `state` | `'pending' \| 'syncing' \| 'dropped'` | `syncing` falls back to `pending` on app start |
| `attempts` | number | Network failures only; backoff 5 s → 60 s |
| `error` | string \| null | The `errors.*` code when `dropped` |
| `label` | string | Lesson title or shift date for the "Not saved" sheet, saved at enqueue time |

Indexes: `[userId+state]`, `[userId+recordKey]`, `createdAt`.

**State transitions**

```
enqueue ─► pending ──sync──► syncing ──applied/duplicate──► (deleted; later same-record entries rebased)
              ▲                 │
              └──network error──┘
                                └──dropped──► dropped ──student dismisses──► (deleted)
```

Coalescing (only against a `pending` entry with the same `recordKey`):
- Save after save → payload replaced, `base` and `at` kept.
- Submit after save → becomes Submit with the new `at`.
- `progress.undo` after `progress.complete` (or the reverse) → both removed.
- `shift.delete` after a new-shift `shift.save` → both removed. After an edit → becomes `shift.delete` with the edit's `base`.

## 3. Validation rules (from the spec)

- FR-003a: at most 5 photos per draft, each ≤ 2 MB after resizing; text ≤ 004's byte limit (`bodyMdSchema`).
- FR-003b: the server never applies an op whose base differs from the current row (R7 table).
- FR-003c: user-facing times accept `at` only in [serverNow − 14 d, serverNow + 2 min] and not before the base version; otherwise server time is used (R8).
- US2 scenario 1: at most 20 MB of media per kept course.
- Rotation patterns, Notes, settings and all Admin writes have no op type: they can't be queued (R14).
