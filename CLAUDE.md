# StudyMate — guide for Claude Code

One mobile-first PWA with two roles (Student, Admin) for planning lessons, deadlines, shifts and reminders.

## Read before any work
1. `.specify/memory/constitution.md` — non-negotiable rules (roles + RLS, test-first, time rules, mobile-first, 3 languages, stack).
2. `docs/technical-spec.md` + `docs/data-model.md` — the HOW (data model, ER diagrams, Prisma rules): architecture, folder structure, auth flows, data model, RLS, TanStack Query patterns, notifications, PWA, theming, testing, deployment.
3. The feature spec you are working on in `specs/NNN-*/spec.md` — the WHAT: user stories, acceptance criteria, requirements.
4. The screenshots that spec lists, in `screenshots/` — the visual target. Match layout, hierarchy and copy.

If these disagree: constitution > feature spec (behaviour) > technical spec (implementation) > screenshots (visuals). Flag the conflict instead of guessing.

## Stack (fixed)
Next.js 16 App Router · TypeScript strict · Supabase (`@supabase/ssr` for auth/storage/realtime) · Prisma 7 (all DB access) · TanStack Query v5 (all data fetching) · Tailwind CSS v4 · shadcn/ui · `@uiw/react-md-editor` · next-intl · next-themes · Serwist · Dexie · Resend · Vercel · pnpm.

## Working rules
- Schema changes: edit `prisma/schema.prisma`, generate a new migration with `prisma migrate diff`, add RLS policies to it, never drop SQL-only objects (see `docs/data-model.md` §4 and §7). `0_init` is the starting schema.
- **Prisma bypasses RLS: every Route Handler and Server Action calls a guard from `src/server/auth/guards.ts` first**, and every Prisma `where` is scoped to the current user.
- Reads: Prisma in `src/features/<feature>/repo.ts` → Route Handler `src/app/api/**/route.ts` → `queryOptions` in `queries.ts`. Writes: `useMutation` → Server Action in `actions.ts` with a Zod schema from `schemas.ts`.
- supabase-js only for Auth, Storage (uploads, signed URLs, copy, delete) and Realtime — never for table queries.
- UI text goes in `src/i18n/messages/{en,my,ja}.json` — never hard-coded.
- Colours from theme tokens only; tap targets ≥ 44 px; test at 390×844.
- Times: store UTC, show in the viewer's timezone; overnight shifts are one record.
- Never put secrets in code or commits; use `.env.local` (git-ignored).

## Engineering practices
These are defaults. The constitution and specs win if they disagree.
- **Look before you write (DRY).** Search `src/lib/`, `src/components/shared/` and the feature folder before adding a helper, hook or component. Extract shared code on the third copy, not the second: a wrong abstraction costs more than a little duplication.
- **One source of truth.** Get types from the Prisma Client and `z.infer<typeof schema>`, never from hand-copied interfaces. Forms and actions share one Zod schema. Text comes from the message files and colours from tokens.
- **Code lives where it's used.** Code used by one feature stays in `src/features/<feature>/`. Code used by two or more moves to `src/lib/` (logic) or `src/components/shared/` (UI). Don't import another feature's internals; move them to a shared place first. `src/components/ui/` is generated by shadcn: compose its components, don't edit them.
- **KISS / YAGNI.** Build what the current spec and task ask for. Don't add options, flags or generic layers "for later". Choose the plain solution a reviewer can follow in one read.
- **Single responsibility.** Keep Route Handlers and Server Actions thin: guard → validate → repo/logic → return. Put business rules (time math, locking, ordering, progress) in pure functions that don't depend on the framework, like `lib/time.ts` or `courses/lock.ts`, so they can be unit-tested. Components render. Reads go in `queries.ts` and writes go through `useMutation`.
- **Small units.** Split a function or component when part of it deserves its own name. Above ~3 parameters, pass one object.
- **Naming.** Names say *what*, not *how*: `isLessonLocked`, `getStudentCourses`. Booleans start with `is`/`has`/`can`. Files are kebab-case.
- **Errors go through the existing wrappers.** Server Actions use `action()` + `fail(code)` (`src/lib/action.ts`). Route Handlers use `handle()` + `NotFound`/`HttpError` (`src/lib/http.ts`). The UI shows errors with `useErrorMessage()`. Error codes are snake_case and need an `errors.*` key in all 3 message files. Never swallow an error or return `null` to mean "failed".
- **Types.** No `any`. Don't use `!` or `as` just to quiet the compiler. Narrow the type, or parse with Zod where data enters (bodies, params, search params). Take the user's id from the guard result, never from client input.
- **Data access.** Select only the columns you need. Avoid N+1 queries (use `include` or `where: { id: { in } }`). Paginate lists that can grow.
- **Comments explain *why*.** Cite the spec or research decision behind non-obvious code (e.g. `spec 002 R13`). No commented-out code, no stray `console.log`, no TODO without a task ID.
- **Focused diffs.** One concern per commit. Don't reformat or refactor unrelated code inside a feature change; note it as a follow-up instead. Delete dead code rather than leaving it in.
- **Tests check behaviour.** Test what the code does, not how it does it, with one behaviour per test. A bug fix starts with a failing test.

## Commands
```
pnpm dev            # Next.js dev server
pnpm typecheck      # tsc --noEmit
pnpm lint
pnpm test           # Vitest
pnpm test:e2e       # Playwright
pnpm test:db        # pgTAP RLS/function tests (supabase/tests) against DIRECT_URL
pnpm prisma migrate deploy     # apply prisma/migrations to DIRECT_URL
pnpm prisma generate           # regenerate client after schema changes
```
`.env` points at the **dev** Supabase project (no local Supabase/Docker). New migrations: `docs/data-model.md` §7 (diff `schema.prisma` against git, never `migrate dev` or `--from-config-datasource`).

## Done means
Acceptance scenarios of the user story pass in Playwright, guard and RLS tests pass, typecheck and lint are clean, and the screen matches its screenshot at phone width.
